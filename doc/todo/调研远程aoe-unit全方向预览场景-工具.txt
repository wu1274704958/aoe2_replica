• 请先对 RecoilEngine 的调试绘制能力进行只读调研，并据此设计、实现一个专用于 AOE Unit 锚点校准的可视化测试场景。

  目标是直观验证并校准远程单位在各朝向下的：

  - 碰撞器（Collision Volume）
  - 受击点（aim_local / aimPos）
  - Projectile 发射点（weaponN_muzzle_local / weaponMuzzlePos）
  - Unit 局部前向、右向、上向，以及 Projectile 初始方向

  本阶段仅支持远程单位，并先以 u_arc_archer 为样例完成闭环；近战 Unit、逐帧手部 socket、箭矢视觉锚点暂不纳入本次范
  围。

  ## 一、先调研 Recoil 原生 Debug Draw 能力

  请梳理并说明 Recoil 中可复用的调试绘制与交互路径，包括但不限于：

  - C++ 侧的 DebugDrawer、几何绘制、线框、文字、世界坐标标记。
  - LuaRules / LuaUI 中的 gl.* 绘制能力、Spring.* 标记 API、同步与非同步边界。
  - Unit 碰撞体、aimPos、weapon muzzle、Projectile 轨迹是否已有调试显示或可复用的查询 API。
  - 调试 UI、命令、热键、配置项、Lua widget/gadget 的常见实现方式。
  - 调试渲染的生命周期、性能特征及其在 Release/开发构建中的可用性。

  输出关键源码位置、类/函数、调用时机和推荐方案。优先选择现有、稳定、最小侵入的能力；不要自行引入第三方 GUI 或新的渲
  染框架。

  ## 二、构建独立的 AOE Anchor Calibration 场景

  在现有 AOE Blank Map Test 基础上，新增可独立启用的锚点校准模式，例如：

  aoe_anchor_calibration = 1

  启用后不执行双队战斗、Attack Move、死亡或批量压力测试，仅生成用于静态观察和校准的 Unit。

  场景要求：

  - 以 u_arc_archer 为首个样例。
  - 默认生成多个弓手，覆盖所有方向
  - 每个 Unit 保持静止、间距充足、位于地图有效范围内。
  - 所有 Unit 使用同一 AOE Sprite 渲染路径和同一原生 Recoil Unit/Weapon 路径。
  - 场景启动后即拥有全图可见性，方便远距离观察。
  - 布局应基于单位数量、间距和地图尺寸计算，不写死固定坐标。
   - 场景要尽可能独立，需要能被纳入版本管理
    - 需要一份用例文档包含如何配置和启动场景

  - 碰撞体必须展示 Recoil 实际用于 Projectile Collision 的最终位置，而非仅显示 UnitDef 原始配置。

  - 受击点必须同时展示 aimPos 与碰撞体中心，便于发现二者不一致。
  - 不要通过 Lua 重新计算一套近似坐标替代引擎真实数据。
  - Debug Draw 必须是可关闭的，关闭后不影响正常 AOE 场景和普通游戏。

  ## 四、动态校准交互

  为场景提供简洁的运行时调节能力。优先采用 Recoil 既有 LuaUI/Widget、命令或调试控制方式，并明确同步边界。

  至少支持选择当前校准对象，并调整：

  aim_local.x / y / z
  weapon1_muzzle_local.x / y / z
  weapon1_forward_local.x / y / z
  collisionVolumeScales.x / y / z
  collision centre / collision offset
  AOE Sprite pixels-to-world 比例
  Unit heading

  交互要求：

  - 支持步进增减与可配置步长。
  - 每次修改后立即更新 Debug Draw。
  - 对会影响原生 Gameplay 的数据，明确其是仅本地预览、测试场景运行时覆盖，还是已重新创建 Unit 后生效。
  - 不要在网络同步游戏中通过非同步 UI 直接修改真实 Gameplay 状态。
  - 提供恢复当前 Def 默认值的操作。
  - 支持复制当前校准结果到日志或剪贴板友好的文本格式。

  ## 五、保存与 Def 回写可行性

  请重点调研并实现一个安全的保存方案；不要让运行时调参直接、无确认地覆写手工维护的 Def 文件。

  优先采用以下分层设计：

  1. 运行时预览层
      - 仅影响校准场景中的测试 Unit；
      - 便于快速观察，不修改磁盘文件。

  2. 导出层
      - 将当前参数导出为结构化 Lua 片段或 JSON；
      - 输出原始 DAT 数据、转换 profile、调整后 anchor、collision 配置及必要注释；
      - 输出应可直接复制到对应 UnitDef 的 customParams / collision 配置。

  3. 可选受控写回层
      - 仅在明确点击“导出到指定文件”后执行；
      - 固定允许写入的测试 Def 或 override 文件，不修改任意路径；
      - 默认生成独立 override/patch 文件，不直接改写 defs.lua；
      - 若确实支持回写，必须先校验目标路径、创建备份或提供明确 diff 预览；
      - 不得修改 AOE manifest 原文件、缓存资源、引擎核心 Def 或无关配置。

  请说明 Recoil Lua 沙箱是否允许安全文件写入；如果不适合在引擎内实现，提供由工具侧读取导出文件并生成 Def patch 的替
  代方案。

  ## 六、验证与交付

  完成后请验证：

  - 各方向弓手均正确生成，AOE Sprite、碰撞器、aim 点和 muzzle 点可同时观察。
  - 转动 Unit 时，碰撞器、aim、muzzle 和方向向量的关系符合预期。
  - 当前 placeholder S3O midPos 不会再次导致碰撞中心偏移。
  - 动态调整能够立即反映在画面和诊断数据中。
  - 导出的配置可用于更新 u_arc_archer Def。
  - 关闭校准模式后，现有双队战斗、Projectile、AOE Renderer 与 Gameplay Bridge 行为不变。
  - Debug Draw 不引入逐帧动态分配、单位级大量 Draw Call 或明显性能回退。
  - 不提交生成日志、截图、构建目录或 AOE 原始资源。
